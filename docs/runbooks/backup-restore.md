# Резервная копия и восстановление

Владелец: владелец продукта · Исполнитель: разработчик/администратор

Supabase Free **не делает автоматических резервных копий** [S9]. Облачная БД — не бэкап.

## Регулярная копия
- Когда: перед каждой демонстрацией, после значимых изменений данных, минимум раз в неделю пилота.
- `npm run db:export` → `backups/<время>/data.json` (все бизнес-таблицы) и `files/` (вложения). Хранить вне репозитория в корпоративном хранилище с ограниченным доступом: копия содержит все данные стенда.

## Восстановление (проверено тестом AT-15)
1. Новый проект Supabase (или проект №2 Free): применить миграции `npm run db:apply` (без `--seed`).
2. Создать пользователей с теми же email: `npm run seed:users` (или консоль Supabase). Идентификаторы будут новыми — восстановление сопоставит их по email.
3. В `.env.local` указать `DATABASE_URL`/`VITE_SUPABASE_URL`/`SUPABASE_SECRET_KEY` нового проекта.
4. `npm run db:restore -- backups/<время> --confirm-wipe` — бизнес-данные целевого проекта заменяются копией в одной транзакции, затем загружаются файлы.
5. Сверка: вход двух ролей, «Сегодня», сальдо начислений (`Роялти → Начисления`), открытие файла, количество заказов и обращений.
6. Переключить сборку на новый проект: обновить `.env.local` и `npm run deploy`.

## Ограничения
- Пароли пользователей не переносятся (их нет в копии) — новые пароли из `seed:users` раздаются заново.
- Цели production RPO ≤ 1 ч / RTO ≤ 4 ч прототипом не обеспечиваются (COST-13); для production — PITR платного тарифа или собственный PostgreSQL с WAL-архивом.
