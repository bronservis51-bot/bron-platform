# Процессы

Для каждого процесса: цель, вход, владелец, исполнители, резервная роль, состояния и переходы (кто и при каком условии), SLA, выход, исключения, связанные инструкции и показатель результата. Роли — коды из [domain-model.md](domain-model.md#роли-и-разрешения). Имена людей не используются.

Обозначения: **Владелец** отвечает за результат процесса; **Исполнитель** — очередь роли; **Резерв** — роль, получающая работу при отсутствии исполнителя; **Подтверждает** — кто фиксирует ключевой результат.

## Карта процессов

```
             ┌───────────── CRM (demo) ─────────────┐
             ▼                                      │
 P-OPEN Открытие точки ──► P-LEARN Обучение/ознакомления
   │  │                        ▲
   │  └─► P-BUY Заказ (стартовый комплект) ─► «МойСклад» (demo) ─► доставка
   │
   ▼
 Точка работает ──► P-SUP Обращения ──► P-KB Знания (решение → инструкция)
   │                   ▲
   ├─► P-BUY Регулярные заказы
   │
   └─► P-ROY Отчёт → расчёт → начисление → оплата → распределение → закрытие
                                               ▲
                              банк/финсистема (demo, следующий этап)

 Сквозные: P-TASK задачи и очереди · P-ACCESS доступ и передача дел · P-INT обмен с внешними системами · P-AUDIT аудит
```

## P-ACCESS Доступ и передача дел

| | |
| --- | --- |
| Цель | У каждого пользователя ровно те полномочия, которые нужны для работы, на нужный срок |
| Владелец | Руководитель (founder) |
| Исполнитель | `hr_admin`, `sysadmin` (разрешение `access.manage`) |
| Резерв | `founder` |
| Вход | Новый сотрудник/партнёр, изменение обязанностей, отпуск, увольнение |
| Выход | Действующие назначения с периодом; работа уволенного в очереди роли |

Переходы назначения: `активно` → `отозвано` (команда `revoke_assignment`, причина обязательна) · `активно` → `истекло` (наступила `valid_to`).
Правила: нельзя назначать себе; нельзя назначать роль, содержащую разрешения, которых нет у назначающего в той же области; партнёрские роли назначаются только в область партнёра или его точки.
Исключения: отзыв последнего исполнителя очереди → очередь попадает в список конфигурационных ошибок (CORE-07).
При отзыве: незавершённые задачи пользователя в этой области → `assignee = null`, остаются в очереди роли; событие в истории задачи.
Показатель: число очередей без активного исполнителя = 0.

## P-TASK Задача

Состояния и переходы (CORE-04):

| Из | В | Команда | Кто | Условие |
| --- | --- | --- | --- | --- |
| planned | ready | автоматически | система | все зависимости `done` |
| ready | in_progress | `task_start` | исполнитель или член очереди (берёт себе) | — |
| in_progress | waiting_external | `task_transition` | исполнитель | причина |
| in_progress | blocked | `task_transition` | исполнитель | причина |
| waiting_external, blocked | in_progress | `task_transition` | исполнитель | — |
| in_progress | in_review | `task_transition` | исполнитель | если шаг требует проверки; результат заполнен |
| in_progress | done | `task_complete` | исполнитель | результат; доказательство, если требуется; проверка не требуется |
| in_review | done | `task_complete` | проверяющий (`task.manage` в области) | проверяющий ≠ исполнитель |
| in_review | in_progress | `task_transition` (return) | проверяющий | причина обязательна |
| любое активное | cancelled | `task_cancel` | `task.manage` | причина |
| done | in_progress | `task_reopen` | `task.manage` | причина; запись в журнал |

Просрочка — вычисляемый признак: `due_at < now()` и статус не `done`/`cancelled`. Комментарий не меняет статус.
Плановые задачи (напоминание о сдаче отчёта, пересмотр статьи) создаются с ключом `dedupe_key = kind:subject:period`, уникальным в БД.

## P-OPEN Открытие франшизной точки

| | |
| --- | --- |
| Цель | Точка открывается в срок, со всеми обязательными условиями, а партнёр понимает, что от него ждут |
| Владелец | Руководитель франшизы (`direction_head`) |
| Исполнители | `franchise_manager` (владелец проекта), профильные очереди: `procurement`, `warehouse`, `support_specialist`, `designer`, `hr_admin`, `finance`; партнёр — шаги стороны партнёра |
| Резерв | `direction_head` |
| Подтверждает | Разрешение на открытие — `opening.approve` (руководитель запуска) |
| Вход | Ручное создание или событие CRM «сделка на этапе X» (Q-09) |
| Выход | Точка в статусе `active`, фактическая дата открытия, задачи стабилизации |
| SLA | Сроки шагов — в днях относительно старта проекта или плановой даты открытия (из шаблона) |

Состояния проекта:

| Из | В | Команда | Кто | Условие |
| --- | --- | --- | --- | --- |
| — | active | `opening_create` | `opening.manage` | шаблон опубликован; повторное событие CRM с тем же ID сделки возвращает существующий проект |
| active | approved | `opening_approve` | `opening.approve` | все критические шаги до этапа «Готовность» включительно `done`; иначе ошибка со списком блокеров |
| approved | opened | `opening_mark_opened` | `opening.manage` | фактическая дата; точка → `active` |
| opened | completed | `opening_complete` | `opening.manage` | задачи стабилизации завершены |
| active, approved | cancelled | `opening_cancel` | `opening.manage` | причина; будущие задачи → `cancelled`; документы и обязательства сохраняются |

Этапы шаблона (A-13): 1 Вход и договор · 2 Локация · 3 Комплектация · 4 Люди · 5 Системы и стандарты · 6 Готовность · 7 Открытие · 8 Стабилизация (7/14/30 дней — предложено).
Изменение плановой даты (`opening_change_date`): пересчитываются только незавершённые задачи с `due_mode = relative` и якорем `planned_open`; ответ команды — список затронутых задач; причина обязательна.
Исключения: блокирующая задача ждёт внешнего поставщика → статус `waiting_external`, видна в риске даты; отмена после оплаты комплектации → задача финансам на обработку обязательств.
Партнёр видит: этапы, свои шаги, ожидаемые действия компании, сроки, причину блокировки. Не видит: внутренние заметки (`opening_note`), закупочные цены.
Показатель: срок открытия = фактическая дата − дата создания проекта; доля открытий без сдвига плановой даты.

## P-SUP Обращение в поддержку

| | |
| --- | --- |
| Цель | Ни одно обращение не теряется; партнёр знает, кто отвечает и когда |
| Владелец | Руководитель сопровождения (`direction_head`) |
| Исполнитель | Очередь компетенции из таблицы маршрутизации: `procurement` (плёнка и доставка), `support_specialist` (оборудование, качество), `designer` (ПО/лекала), `finance` (отчётность/роялти), `franchise_manager` (маркетинг, обучение, другое) |
| Резерв | `franchise_manager`, затем `direction_head` |
| Подтверждает | Автор обращения (подтверждение решения) или автоматически по истечении периода переоткрытия |
| SLA | Первая реакция и решение — отдельные таймеры по календарю очереди; при `stopped` (точка не работает) — срочная эскалация сразу руководителю |

Состояния:

| Из | В | Команда | Кто | Условие |
| --- | --- | --- | --- | --- |
| — | new | `ticket_create` | автор с `ticket.create` в области точки | категория, точка, описание; срочность `stopped` требует пояснения |
| new | assigned | `ticket_assign` / `ticket_take` | `ticket.work` в очереди | — |
| assigned | in_progress | `ticket_reply` (первый ответ сотрудника) | исполнитель | фиксирует первую реакцию |
| in_progress | waiting_partner | `ticket_transition` | исполнитель | таймер решения на паузе |
| waiting_partner | in_progress | ответ автора / `ticket_transition` | автор или исполнитель | пауза закрывается, срок решения сдвигается на длительность паузы |
| in_progress | waiting_vendor | `ticket_transition` | исполнитель | таймер не останавливается; риск виден |
| in_progress, waiting_* | resolved | `ticket_resolve` | исполнитель | причина решения обязательна; ссылка на статью, если есть |
| resolved | closed | `ticket_confirm` | автор; или автоматически через N дней (настройка, демо — 3) | — |
| resolved | in_progress | `ticket_reopen` | автор | в пределах периода переоткрытия |

Внутренние сообщения (`internal = true`) не видны партнёрским ролям.
Исключения: нет исполнителя в очереди → назначение резервной роли и уведомление; просрочка реакции → эскалация руководителю очереди (дедупликация уведомлений).
Показатель: доля обращений с соблюдёнными таймерами; обращения без ответственного = 0.

## P-BUY Заказ расходников

| | |
| --- | --- |
| Цель | Заказ не теряется, имеет один идентификатор, статус и строки совпадают со складом |
| Владелец | Руководитель снабжения (`procurement` + `direction_head`) |
| Исполнители | Автор (партнёр / управляющий точкой), `procurement` (согласование), `warehouse` (сборка/отгрузка во внешней системе), `finance` (подтверждение оплаты заказа) |
| Резерв | `direction_head` |
| Подтверждает | Получатель (приёмка количеств) |

Вид заказа задаёт правила (BUY-04): `partner_order` — коммерческий заказ партнёра, `prepay` по умолчанию (A-09); `supply_request` — заявка собственной точки, согласование при сумме выше порога.

Основное состояние `status` и независимые измерения:

| Измерение | Значения |
| --- | --- |
| `status` | draft → submitted → confirmed → in_fulfillment → partially_shipped → shipped → delivered → completed; cancelled |
| `approval_status` | not_required · pending · approved · rejected |
| `payment_status` | not_required · required · reported · confirmed |
| `transfer_status` | not_sent · pending · sent · failed · needs_reconciliation |

Переходы:

| Команда | Кто | Что делает |
| --- | --- | --- |
| `cart_set_line` | автор | черновик; проверка единицы и кратности при отправке |
| `order_submit(key)` | автор | перепроверка прав, цен по текущему прайс-листу, кратности, минимума; снимок цен; `submitted`; если согласование не нужно и оплата не требуется — создаётся команда outbox `warehouse.create_order`. Повтор с тем же ключом возвращает тот же заказ |
| `order_approve` / `order_reject` | `order.approve` | при одобрении — далее как выше |
| `order_payment_confirm` | `payment.confirm` | `payment_status = confirmed` → команда outbox |
| `process_outbox` | система (pg_cron) или оператор | передача в склад; при сбое `transfer_status = failed` и повтор с задержкой; при неизвестном результате — сначала поиск документа по внешнему коду |
| входящее событие склада (inbox) | система | `confirmed` строк, отгрузки с количествами; повтор события игнорируется |
| `order_receive` | получатель | фактически полученные количества по строкам; расхождение → обращение категории «плёнка и доставка» |
| `order_cancel` | автор до `confirmed`; `order.manage` позже | причина |
| `order_repeat` | автор | новая корзина с текущими ценами |

Правило строки: `qty_confirmed ≤ qty_ordered`, `qty_shipped ≤ qty_confirmed`, `qty_received ≤ qty_shipped`. Заказ `delivered`, только когда все незакрытые строки получены; частичная отгрузка оставляет остаток открытым (AT-06).
Показатель: заказы без движения дольше порога; доля заказов, сверенных с внешним документом.

## P-ROY Отчётность и роялти

| | |
| --- | --- |
| Цель | Партнёр и финансы видят одинаковый расчёт и одинаковое сальдо |
| Владелец | Финансовый руководитель (`finance` с `royalty.publish`) |
| Исполнители | Партнёр (`royalty.report.submit`), `finance` (проверка, начисление, оплаты), `franchise_manager` (напоминания) |
| Резерв | `founder` |
| Подтверждает | Отчёт — `royalty.review`; начисление — `royalty.publish`; оплату — `payment.confirm` (≠ регистрирующий при SoD strict) |

Отчёт:

| Из | В | Команда | Кто | Условие |
| --- | --- | --- | --- | --- |
| — | draft | `report_save_draft` | партнёр | договор действует в периоде; точки договора |
| draft | submitted | `report_submit` | партнёр | редакция фиксируется (`locked`); нулевая строка требует причины |
| submitted | in_review | `report_take_review` | финансы | — |
| in_review | needs_correction | `report_return` | финансы | причина |
| needs_correction | submitted | `report_submit` | партнёр | создаётся новая редакция |
| in_review | approved | `report_approve` | финансы | расчёт по действующим версиям политики; при нескольких версиях в периоде — разбивка базы обязательна |
| approved | — | `accrual_publish` | `royalty.publish` | одно действующее начисление вида `royalty` на договор+период |
| approved | closed | `period_close` | `royalty.publish` | начисление опубликовано |
| closed | — | `adjustment_create` | `royalty.publish` | только корректировкой с причиной и ссылкой |

Оплата:

| Из | В | Команда | Кто |
| --- | --- | --- | --- |
| — | reported | `payment_report` | партнёр (квитанция — вложение) — **не уменьшает долг** |
| — / reported | confirmed | `payment_register` + `payment_confirm` | финансы; при SoD strict — разные пользователи |
| reported | rejected | `payment_reject` | финансы, причина |
| confirmed | reversed | `payment_reverse` | финансы, причина; все распределения сторнируются |

Распределение `allocation_create(payment, accrual, amount)`: блокировка строк платежа и начисления (`FOR UPDATE`), проверка `amount ≤ остаток платежа` и `amount ≤ остаток начисления`; второй параллельный запрос видит актуальные суммы и получает конфликт (AT-10). Сторно — `allocation_reverse(reason)`.
Остаток начисления (ROY-11) = начисление + дебетовые корректировки − кредитовые корректировки − действующие распределения подтверждённых платежей. Нераспределённый остаток платежа — аванс.
Напоминания: задача партнёру о сдаче отчёта за N дней до срока; задача/уведомление о просроченной оплате; санкций нет (ROY-13).
Показатели: доля отчётов, сданных вовремя; сбор роялти; просроченная задолженность (только после срока, по валютам раздельно).

## P-KB Знания

| | |
| --- | --- |
| Цель | Сотрудник находит актуальную инструкцию в контексте работы |
| Владелец | Владелец процесса, к которому относится статья (`article.owner_id`) |
| Исполнители | `kb_editor` (редактор), эксперт |
| Резерв | Очередь `kb_editor` |
| Подтверждает | `kb.publish` (≠ автор редакции при SoD strict для обязательных материалов) |

Редакция статьи: `draft` → `in_review` (`article_submit`) → `published` (`article_publish`, утверждает конкретную редакцию) / `rejected` (`article_reject`, причина) → предыдущая опубликованная становится `superseded`.
Статья: `draft` (нет публикаций) · `published` · `needs_review` (наступил `review_due` или сообщение об устаревании) · `suspended` (источник Drive недоступен) · `archived`.
Публикация с флагом «требуется повторное ознакомление» создаёт назначения `ack_assignment` для аудитории обязательной статьи.
Drive (demo): изменение исходника → новая редакция `in_review` с `source = drive`; опубликованная не меняется. Отзыв доступа → статья `suspended`, скрыта из поиска, задача владельцу.
Показатели: просроченные пересмотры; незавершённые ознакомления; безрезультатные запросы.

## P-INT Обмен с внешними системами

Команда в outbox: `pending` → `processing` → `done` | `failed` (повтор с экспоненциальной задержкой, `attempts`) | `unknown` (ответ потерян — следующий шаг сверка) | `dead` (исчерпаны попытки → задача оператору `integration.operate`).
Входящее событие в inbox: уникальность `(source, event_id)`; повтор — `duplicate`, не обрабатывается.
Исключения и действия оператора: «Повторить», «Сверить», «Отметить как решённое вручную» (с причиной). Runbook: [moysklad-unavailable](runbooks/moysklad-unavailable.md), [duplicate-external-order](runbooks/duplicate-external-order.md).
