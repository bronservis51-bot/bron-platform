# ADR-0004 PostgreSQL как граница команд

Статус: принято

## Контекст
API-01/02 требуют единой точки исполнения бизнес-операций и явных команд; COST-19 — атомарности в SQL RPC и запрета прямой записи в защищённые поля. Собственного сервера в прототипе нет.

## Решение
- Таблицы — в схеме `public` (их читает PostgREST), RLS включён на всех; `authenticated` имеет только SELECT, `anon` — ничего.
- Команды — функции `public.<command>(...)` с `SECURITY DEFINER`, `SET search_path = public, app_private, pg_temp`, владельцем `postgres`, `EXECUTE` только для `authenticated`. Первая строка каждой команды — `app_private.require_user()`, затем `require_perm(...)` по области объекта.
- Вспомогательные функции — в схеме `app_private`, которую PostgREST не публикует.
- Представления создаются с `security_invoker = true`, чтобы RLS действовал.
- Supabase по умолчанию выдаёт `anon`/`authenticated` все права на новые таблицы и функции в `public` — последняя миграция отзывает их явно; тест проверяет итоговые grants.

## Альтернативы
Edge Functions как командный слой: TypeScript, но транзакции всё равно через RPC, лишний сетевой переход и квоты. Отклонено для прототипа.

## Последствия
Логика в PL/pgSQL покрывается SQL-тестами на PGlite. Имена команд — стабильный контракт для будущего backend.
