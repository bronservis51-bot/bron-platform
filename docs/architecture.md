# Архитектура

## 1 Прототип (раздел 25): GitHub Pages + Supabase Free

```
 Браузер / установленное PWA (GitHub Pages, HTTPS, статическая сборка)
 ┌──────────────────────────────────────────────────────────────────┐
 │ React UI (экраны модулей)                                         │
 │   └─► прикладные сервисы модулей  src/modules/<module>/api.ts     │
 │          └─► адаптер платформы    src/platform/backend.ts         │
 │                 └─► supabase-js (publishable key, JWT пользователя)│
 │ Service worker: только оболочка приложения; данные не кешируются  │
 │ IndexedDB: черновики и очередь операций, раздельно по user_id     │
 └──────────────────────────────────────────────────────────────────┘
                         │ HTTPS (REST/RPC PostgREST, Auth, Storage)
                         ▼
 Supabase Free
 ┌──────────────────────────────────────────────────────────────────┐
 │ Auth — сессии и пароли                                           │
 │ PostgreSQL                                                        │
 │   public: таблицы модулей (RLS, только SELECT для authenticated)  │
 │           команды RPC: SECURITY DEFINER, search_path зафиксирован │
 │   app_private: проверки доступа, общие функции, обработчики outbox│
 │   outbox / inbox / audit_event / command_log                      │
 │   pg_cron (если доступен): process_outbox, process_inbox, таймеры │
 │ Storage: закрытый bucket private-files, политики через file_asset │
 └──────────────────────────────────────────────────────────────────┘
                         │ (следующий этап: Edge Functions / worker)
                         ▼
   «МойСклад», Google Drive, CRM, банк — в прототипе demo-адаптеры в БД
```

### Принципы

1. **Команды и чтения разделены** ([ADR-0004](adr/0004-database-as-command-boundary.md)). Клиент читает таблицы и представления под RLS. Любое изменение — вызов именованной команды (`report_submit`, `allocation_create`…). Команда в одной транзакции: проверяет пользователя, разрешение и область, проверяет переход состояния и бизнес-ограничения, пишет данные, историю, аудит, уведомления и outbox. У роли `authenticated` нет INSERT/UPDATE/DELETE ни на одной доменной таблице.
2. **Автор и область — из сессии.** Команды берут `auth.uid()`; область вычисляется из объекта, а не принимается из параметров.
3. **Запрет по умолчанию.** RLS включён на всех таблицах; политика чтения вызывает `app_private.has_perm(...)`. Новая таблица без политики недоступна. Тест `security.test.ts` проверяет, что у каждой таблицы `public` включён RLS и нет лишних grants.
4. **Ошибки команд** — `raise exception` с кодом из словаря API-04 в тексте (`forbidden`, `not-found`, `validation`, `version-conflict`, `transition-not-allowed`, `idempotency-conflict`, `integration-pending`) и деталями в `HINT`/`DETAIL`. Адаптер клиента превращает их в типизированную ошибку и понятный текст.
5. **Идемпотентность.** Команды, которые пользователь может повторить (отправка заказа, отчёта, регистрация платежа, распределение), принимают ключ операции; `command_log` хранит отпечаток и результат.
6. **Конкурентность.** Изменяемые сущности имеют `revision`; команды редактирования принимают ожидаемую ревизию. Денежные операции блокируют строки `FOR UPDATE`.
7. **Внешние системы — через outbox/inbox** ([ADR-0005](adr/0005-outbox-and-jobs-on-postgres.md)). Транзакция команды только кладёт запись в outbox; обработчик отдельно выполняет адаптер. В прототипе адаптеры — demo (эмуляция в таблице `demo_external_doc`) с режимами `success`, `fail`, `lost_response` и повторной доставкой входящего события.
8. **Модульные границы** в клиенте: `src/modules/<module>/` содержит `api.ts` (единственное место обращения к backend), типы и экраны. Экран не вызывает supabase-js напрямую; правило проверяется тестом.
9. **Демо отделено от production.** Демо-адаптеры, тестовые договоры и синтетические пользователи помечены в данных (`mode = demo`, `is_test`, `is_demo`) и в интерфейсе (плашка «Демо»).

### Структура репозитория

```
docs/                     документы раздела 1, ADR, runbooks
supabase/migrations/      SQL-миграции по модулям, применяются по порядку
supabase/seed/            синтетические данные (без секретов и реальных людей)
supabase/tests-shim/      эмуляция схем auth/storage Supabase для локальных тестов
scripts/                  сборка SQL, создание демо-пользователей, публикация
src/platform/             адаптер backend, сессия, i18n, офлайн-хранилище
src/ui/                   дизайн-система: токены, компоненты
src/modules/<module>/     api.ts + экраны модуля
tests/db/                 проверки инвариантов и доступа на PGlite
```

## 2 Альтернативы, рассмотренные для прототипа

| Вариант | Плюсы | Минусы | Решение |
| --- | --- | --- | --- |
| GitHub Pages + Supabase Free (команды в SQL) | 0 ₽; общая БД; Auth, Storage, RLS; нет своего сервера | Логика в SQL; ограничения Free; Pages не для бизнеса | **Выбран владельцем** (COST-04) |
| GitHub Pages + Supabase + Edge Functions (TypeScript-команды) | Логика на TS | Транзакция БД из Edge Function — через RPC всё равно; лишний сетевой переход; квоты вызовов | Edge Functions — только для операций с секретами (реальные адаптеры, принудительный выход) |
| Cloudflare Pages/Workers + Neon/Turso | Бесплатные уровни, cookie-сессии | Нужна своя авторизация и хранилище файлов; больше кода | Кандидат на постоянный хостинг, не прототип |
| Локальная демонстрация | Нет ограничений провайдеров | Запрещено COST-04 | Отклонено |

## 3 Целевая архитектура после пилота

Модульный монолит (TypeScript, NestJS или сопоставимый) + отдельный worker + PostgreSQL + S3-совместимое хранилище, по ARCH-01. Путь перехода сохраняет контракты прототипа:

1. Схема PostgreSQL и миграции переносятся как есть (стандартная PostgreSQL; зависимость только от `auth.uid()` и схемы `storage` — изолированы в `app_private.current_user_id()` и функциях файлов).
2. Команды RPC сохраняют имена и сигнатуры; backend сначала вызывает их же, затем по модулю переносит логику в TypeScript (strangler), не меняя клиент — клиент обращается к командам через `src/platform/backend.ts`.
3. Сессия переходит на BFF с HttpOnly cookie ([ADR-0003](adr/0003-session-storage-prototype.md)).
4. Outbox обрабатывает worker вместо pg_cron; таблицы и статусы те же.
5. Клиент (статическая сборка) переносится на любой статический хостинг без изменений — base URL задаётся переменной сборки.

## 4 Ограничения прототипа (явно)

- Нет SLA доступности; проект Supabase может быть приостановлен после 7 дней неактивности.
- Нет автоматических резервных копий — только экспорт по [runbook](runbooks/backup-restore.md).
- Фоновые задания зависят от модуля Cron Supabase; при его отсутствии — ручной запуск из экрана «Интеграции».
- Интеграции — только demo. Никакой статус в прототипе не означает реальную отгрузку или зачисление.
- Push-уведомлений нет; email-рассылок нет (кроме служебных писем Supabase Auth, которые не нужны для демо).
- Поиск не индексирует содержимое вложений.
